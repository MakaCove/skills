# req-code-bug-review

## 目标

本技能只负责对照需求、原型和代码排查 Bug，不负责生成完整测试用例、测试计划或自动化脚本。

最终输出一个文件：`Bug排查报告.md`。

## 可用输入

用户可以提供：

- 需求文档
- 原型图、页面截图或设计稿
- 前端代码
- 后端代码
- 数据库连接 MCP（可选，由用户手动提供）

不要求用户提供：用户角色说明、测试账号、接口文档、接口日志或运行日志。接口和执行路径应从前后端代码中追踪。对于资料中没有明确说明的内容，不要自行编造。

## 数据库 MCP 规则

- 先判断数据库 MCP 是否可用。
- 可用时，只读取审查所需的表结构、字段约束、关联关系和必要数据；不要执行删除、更新或其他破坏性操作。
- 可重点核查唯一约束、非空约束、状态值、数据归属、关联数据、事务一致性和代码读写结果。
- 不可用时继续完成前端和后端代码审查，不得虚构数据库查询结果。
- 依赖真实数据库才能确认、又没有数据库连接时，结论写“需要运行验证”，验证依赖写“数据库待确认”。
- 不查询与当前业务无关的敏感数据。
- 不修改任何环境的数据。
- 一条样本只说明该样本的现象，不直接推论所有单据或记录都存在同样问题。

## 分析流程

1. 从需求文档提取明确的目标行为、限制条件、状态规则和权限规则。
2. 从原型图确认页面入口、操作入口、字段状态、成功结果、失败结果和跳转行为。
3. 从前端入口追踪事件处理、参数组装、接口请求、响应处理和页面状态更新。
4. 从后端入口追踪参数校验、业务判断、权限判断、数据读写、事务和异常分支。
5. 对照需求和原型比较预期行为与代码实际可达行为。
6. 如果数据库 MCP 可用，核查数据库约束和真实数据是否支持代码结论。
7. 对每个问题给出证据、触发条件、影响、严重程度和结论置信度。

下结论前必须按照 `references/生命周期核对.md` 逐层核对适用内容，并在报告中记录每项是“已检查”“本功能没有这一层”“材料缺失”还是“需要运行验证”。只读主流程而没有完成逐层核对时，不得写“未发现明显问题”。

## 重点审查范围

- 功能遗漏或入口不可达
- 页面行为与原型不一致
- 前后端校验不一致
- 后端缺少必要校验
- 权限或数据归属校验缺失
- 非法状态流转
- 重复提交和重复数据
- 接口失败却展示成功
- 数据保存后页面状态错误
- 空值、异常响应或边界数据导致错误
- 删除、撤销、审批等操作限制缺失
- 分页、筛选、排序和搜索逻辑错误
- 金额、数量、时间和状态计算错误
- 数据库约束缺失或与代码逻辑冲突
- 部分成功、事务未回滚和数据不一致

以上审查项都必须在报告的“审查覆盖”中留下状态，不能因为没有发现问题就省略。

## 结论分类

每个问题必须使用以下一种结论：

- `已确认 Bug`：需求或原型依据明确，且代码路径能够确定地产生错误结果；如果没有实际运行，只能写“代码路径确认”，不能写成“已实际复现”。
- `高概率 Bug`：代码存在明显风险，但仍依赖未确认条件。
- `需要运行验证`：必须实际操作页面、调用接口或查询环境才能确认。
- `需求不明确`：需求和原型不足以确定正确行为。
- `未发现明显问题`：在当前提供的资料范围内没有发现有充分证据支持的问题。

不要因为个人习惯、代码风格或未定义行为直接判定为 Bug。

“数据库待确认”不是独立结论。依赖数据库但没有数据库 MCP 时，结论使用“需要运行验证”，并在验证依赖中写“数据库待确认”。

## 严重程度

- P0：权限绕过、敏感数据泄露、资金错误、数据大面积损坏或系统不可用。
- P1：核心业务无法完成、关键数据错误或重要状态错误。
- P2：重要功能异常，但存在替代路径。
- P3：一般体验、提示、展示或低风险边界问题。

严重程度必须结合影响范围说明，不能只给等级。

## Bug 证据要求

每个 Bug 必须包含：

- 问题标题
- 严重程度
- 结论分类和置信度
- 影响模块和影响范围
- 需求依据
- 原型依据（适用时）
- 前端或后端代码位置
- 数据库依据（适用时）
- 触发条件
- 复现或推导步骤
- 预期行为
- 当前代码行为
- 根因分析
- 修复方向
- 是否需要运行验证

不能只给代码片段或一句“这里可能有问题”。必须解释从输入到错误结果的完整路径。

修复方向只写一句高层处理方向，例如“补充后端数据归属校验”，不写补丁、具体代码或 SQL。

每条问题固定增加三个字段：

- `结论`：已确认 Bug / 高概率 Bug / 需要运行验证 / 需求不明确
- `证据状态`：需求和代码均明确 / 原型和代码明确 / 仅代码推导 / 仅数据库现象 / 需要运行验证
- `运行状态`：未实际运行 / 已运行验证 / 部分运行验证

同一根因影响多个页面、接口或任务入口时合并为一条问题，在该问题下列出全部受影响入口，不按页面重复拆号。

## 输出文件

只输出一个 `Bug排查报告.md`，包含以下部分：

1. `审查范围`：输入资料、代码范围、数据库 MCP 状态和审查限制。
2. `审查覆盖`：哪些需求已经追到页面、前端、后端和数据库，逐项写核对状态。
3. `未审查范围`：因缺代码、缺原型、缺数据库或缺运行环境而不能下结论的范围。
4. `总体结论`：各类问题数量和未发现明显问题的模块。
5. `已确认问题`：有充分证据支持的 Bug。
6. `高概率问题`：风险明显但需要补充条件的问题。
7. `需要运行验证`：静态分析无法确认的问题。
8. `需求或原型不明确项`：无法作出确定判断的内容。
9. `数据库核查结果`：仅在提供数据库 MCP 时填写具体核查结果。

没有发现 Bug 时仍然输出该文件，并明确写出审查范围和“当前资料范围内未发现有充分证据支持的 Bug”。

不要额外输出测试用例文件、测试计划、自动化脚本或其他附件。

## 禁止误判

- 不把需求未定义的行为直接判定为缺陷。
- 不把代码当前行为直接当作需求预期。
- 不把静态推导写成已实际复现。
- 不把缺少数据库 MCP 写成数据库已验证。
- 不为了增加问题数量而重复拆分同一个根因。
