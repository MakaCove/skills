# req-code-bug-review

## 目标

本技能只负责对照需求、原型和代码排查 Bug，不负责生成完整测试用例、测试计划或自动化脚本。

用户给出已有用例时，用例只是额外检查清单，需求、原型和代码的排查照旧全做，不能只按用例查。没有用例时直接开始，不索要、不等待，也不调用其他技能生成用例。

最终输出一个文件：`Bug排查报告.md`。

## 可用输入

用户可以提供：

- 需求文档
- 原型图、页面截图或设计稿
- 前端代码
- 后端代码
- 已有测试用例文件（可选，有就额外对照）
- 数据库 MCP（可选。当前已经连上就只读参考，没连上继续做，不向用户索要）

不要求用户提供：用户角色说明、测试账号、接口文档、接口日志或运行日志。接口和执行路径应从前后端代码中追踪。对于资料中没有明确说明的内容，不要自行编造。

## 项目定位和参考文件

用户本次指定的项目、路径和输出目录优先；缺省值读取 [config/projects.json](config/projects.json)。按指定项目选择 `projects` 中的同名项；只有本次没有项目线索时才使用 `default_project`。校验项目键和目录是否存在，不得把 OMS 的前端与 WMS 的后端混用。配置无效或路径不存在时继续处理已提供的材料，在“未审查范围”记录缺口，不猜测其他项目路径。只有无法确定要审查哪个项目时才询问项目选择，不索要可选资料。

在报告“审查范围”中记录实际代码目录、需求或原型版本（已知时），以及前后端各自的分支、提交号和是否有本地改动（Git 可用时）。结论只针对实际读取的代码。

| 阶段 | 读取的参考 | 职责 |
|---|---|---|
| 提取规则和追踪入口前 | [材料抽取.md](references/材料抽取.md) | 记录预期、来源和实际代码路径 |
| 业务链路核对时 | [生命周期核对.md](references/生命周期核对.md) | 逐层核对业务行为，按代码中实际存在的机制追加检查 |
| 将候选问题定性前 | [判定.md](references/判定.md)、[核对合同.md](references/核对合同.md) | 排除其他保护机制，区分问题结论与证据状态 |
| 生成报告前 | [清单格式.md](references/清单格式.md)、[输出.md](references/输出.md) | 使用统一字段，核对覆盖及单文件交付 |
| 需要写法示例时 | [示例.md](references/示例.md) | 参考证据链写法，不复制示例的业务规则和路径 |

## 数据库 MCP 规则

执行开始时先看当前环境里有没有已经连上的数据库 MCP。这不是开工条件。

- 已经连上：只读取审查所需的表结构、字段约束、关联关系和必要数据，当作参考。不要执行删除、更新或其他破坏性操作。
- 可重点核查唯一约束、非空约束、状态值、数据归属、关联数据、事务一致性和代码读写结果。
- 不可用时继续完成前端和后端代码审查，不得虚构数据库查询结果。
- 依赖真实数据库才能确认、又没有数据库连接时，结论写“需要运行验证”，验证依赖写“数据库待确认”。
- 不查询与当前业务无关的敏感数据。
- 不修改任何环境的数据。
- 一条样本只说明该样本的现象，不直接推论所有单据或记录都存在同样问题。

## 分析流程

1. 从需求文档提取明确的目标行为、限制条件、状态规则和权限规则。
2. 从原型图确认页面入口、操作入口、字段状态、成功结果、失败结果和跳转行为。
3. 从前端入口追踪事件处理、参数组装、接口请求、响应处理和页面状态更新。
4. 从后端入口追踪参数校验、业务判断、权限判断、数据读写、事务和异常分支。
5. 对照需求和原型比较预期行为与代码实际可达行为。
6. 当前已经连着数据库 MCP 时，核查数据库约束和真实数据是否支持代码结论。没连上就跳过这一步，不索要连接。
7. 对候选问题核查公共校验和实际可达性，再按判定与核对合同给出结论、证据状态、运行状态和严重程度。不另设置信度或证据等级。
8. 用户给了测试用例时，在完成上面全部步骤之后，再按「用例对照」把要用的用例追到代码。没给用例就跳过这一步。

下结论前必须按照 `references/生命周期核对.md` 逐层核对适用内容，并在报告中记录每项是“已检查”“本功能没有这一层”“材料缺失”还是“需要运行验证”。只读主流程而没有完成逐层核对时，不得写“未发现明显问题”。有用例时也不能用用例对照代替这次逐层核对。

没有在当前方法看到校验，不等于整条链路没有校验；还需检查适用的网关、拦截器、注解、切面、父类、公共服务和持久化约束。保护机制的实现或配置未读到时，不能认定它不存在。并发、幂等、事务、消息和缓存只在当前业务实际存在相关路径时核对，不套用无依据的故障场景。

## 用例对照

没给用例时，报告「用例对照」只写「本次无用例，按需求、原型和代码排查」。

给了用例时，需求、原型、代码和生命周期核对已经做完，再追加对照。用例没写到的入口、空值、清空旧值、失败后的下一轮，仍然以生命周期核对为准。

正确结果以需求和原型为准。

- 需求和用例一致，完整可达代码路径确定得到错误结果：按判定规则记录 Bug，写上用例编号和需求依据。
- 需求明确但用例预期不一致：在用例对照的“说明”中标记“用例预期有误，未采用”，以需求继续核对代码；不把用例错误归为“需求不明确”。预期标了待确认时也先注明未采用；只有需求或原型本身存在歧义时才写入“需求不明确”。
- 代码里找不到该场景的入口：写“代码中未找到该场景”，再区分材料缺失、搜索尚未完成、已确认未实现或外部实现待验证，处理规则见 `references/判定.md`。不能一律开 Bug 或一律写“需要运行验证”。
- 代码路径和用例预期一致：对照结果写「与代码路径一致」。没有真正运行过页面时，不写已通过。

要追的用例：

- P0、P1 全部追。
- P2、P3 里走主流程、覆盖主要业务功能的，也要追。
- 其余 P2、P3，例如提示、文案、低风险体验，太多时可以不逐条追，但要写明没追哪些。

同一根因被多条用例碰到时合并为一条，下列出这些用例编号。

对照结果使用：`与代码路径一致`、`与代码路径不一致`、`用例预期有误未采用`、`预期待确认未采用`、`代码中未找到该场景`。对照表增加“说明”列，记录未采用原因、搜索范围或缺少的材料。

## 重点审查范围

- 功能遗漏或入口不可达
- 页面行为与原型不一致
- 前后端校验不一致
- 后端缺少必要校验
- 权限或数据归属校验缺失
- 非法状态流转
- 重复提交和重复数据
- 接口失败却展示成功
- 数据保存后页面状态错误
- 空值、异常响应或边界数据导致错误
- 删除、撤销、审批等操作限制缺失
- 分页、筛选、排序和搜索逻辑错误
- 金额、数量、时间和状态计算错误
- 数据库约束缺失或与代码逻辑冲突
- 部分成功、事务未回滚和数据不一致

以上审查项都必须在报告的“审查覆盖”中留下状态，不能因为没有发现问题就省略。

## 结论分类

缺陷候选使用下列结论，需求不明确另列待确认规则；“未发现明显问题”只用于总体说明：

- `已确认 Bug`：需求或原型依据明确，完整可达代码路径确定地产生错误结果，且已排除相关公共保护机制或替代实现。可以通过静态证据确认；没有实际运行时，运行状态必须写“未实际运行”。
- `高概率 Bug`：代码存在明显风险，但仍依赖未确认条件。
- `需要运行验证`：必须实际操作页面、调用接口或查询环境才能确认。
- `需求不明确`：需求和原型不足以确定正确行为。
- `未发现明显问题`：仅用于已完成核对范围的总体结论，不作为一条 Bug；材料缺失的范围必须单列，不得据此推断无问题。

不要因为个人习惯、代码风格或未定义行为直接判定为 Bug。

“数据库待确认”不是独立结论。依赖数据库但没有数据库 MCP 时，结论使用“需要运行验证”，并在验证依赖中写“数据库待确认”。

## 严重程度

- P0：权限绕过、敏感数据泄露、资金错误、数据大面积损坏或系统不可用。
- P1：核心业务无法完成、关键数据错误或重要状态错误。
- P2：重要功能异常，但存在替代路径。
- P3：一般体验、提示、展示或低风险边界问题。

严重程度必须结合影响范围说明，不能只给等级。

## Bug 证据要求

每个 Bug 必须包含：

- 问题标题
- 严重程度
- 结论、证据状态和运行状态（见下方枚举，不另设置信度）
- 影响模块和影响范围
- 需求依据
- 原型依据（适用时）
- 前端或后端代码位置
- 数据库依据（适用时）
- 触发条件
- 复现或推导步骤
- 预期行为
- 当前代码行为
- 根因分析
- 已核查的公共保护机制、替代实现，以及仍未确认的条件
- 修复方向
- 是否需要运行验证

不能只给代码片段或一句“这里可能有问题”。必须解释从输入到错误结果的完整路径。

修复方向只写一句高层处理方向，例如“补充后端数据归属校验”，不写补丁、具体代码或 SQL。

每条缺陷候选固定增加三个字段（需求不明确的规则项按报告模板另列，不硬填运行证据）：

- `结论`：已确认 Bug / 高概率 Bug / 需要运行验证 / 需求不明确
- `证据状态`：需求和代码均明确 / 原型和代码明确 / 仅代码推导 / 仅数据库现象 / 需要运行验证
- `运行状态`：未实际运行 / 已运行验证 / 部分运行验证

同一根因影响多个页面、接口、任务入口或用例时合并为一条问题，在该问题下列出全部受影响入口和用例编号，不按页面或用例重复拆号。

## 输出文件

只输出一个 `Bug排查报告.md`，包含以下部分：

1. `审查范围`：输入资料、代码范围、数据库 MCP 状态和审查限制。
2. `审查覆盖`：哪些需求已经追到页面、前端、后端和数据库，逐项写核对状态。
3. `未审查范围`：因缺代码、缺原型、缺数据库或缺运行环境而不能下结论的范围。
4. `总体结论`：各类问题数量和未发现明显问题的模块。
5. `已确认问题`：有充分证据支持的 Bug。
6. `高概率问题`：风险明显但需要补充条件的问题。
7. `需要运行验证`：静态分析无法确认的问题。
8. `需求或原型不明确项`：无法作出确定判断的内容。
9. `数据库核查结果`：仅在提供数据库 MCP 时填写具体核查结果。
10. `用例对照`：给了用例时写对照表；没给用例时写「本次无用例，按需求、原型和代码排查」。

没有发现 Bug 时仍然输出该文件，并明确写出审查范围和“当前资料范围内未发现有充分证据支持的 Bug”。

不要额外输出测试用例文件、测试计划、自动化脚本或其他附件。

## 禁止误判

- 不把需求未定义的行为直接判定为缺陷。
- 不把代码当前行为直接当作需求预期。
- 不把静态推导写成已实际复现。
- 不把缺少数据库 MCP 写成数据库已验证。
- 不为了增加问题数量而重复拆分同一个根因。
- 不把用例预期代替需求或原型预期。
- 不因为已有用例，就只查用例里写到的场景。
