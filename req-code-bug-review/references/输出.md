# 输出

## 最终交付

最终只交付一个文件：`Bug排查报告.md`。输出目录使用用户指定的路径；未指定时读取 `config/projects.json`。

项目选择、配置校验和路径缺失处理遵守 `SKILL.md`；不得静默切换项目。报告引用实际读取的代码目录和可获取的版本，不把工作区代码当成已部署版本。

报告固定包含：

1. 审查范围
2. 审查覆盖
3. 未审查范围
4. 总体结论
5. 已确认问题
6. 高概率问题
7. 需要运行验证的问题
8. 需求或原型不明确项
9. 数据库核查结果（仅在提供数据库 MCP 时填写具体结果）
10. 用例对照（给了用例时填写对照表；没给用例时写明按需求、原型和代码排查）

每条缺陷候选包含标题、结论、证据状态、运行状态、严重程度、需求或原型依据、代码位置、触发条件、预期行为、当前代码行为、影响范围、根因分析、修复方向和验证要求。需求不明确的规则项只填冲突来源和影响范围，不硬填缺陷根因或严重程度。修复方向只写一句高层方向。

“已确认”需满足核对合同的定性门槛；问题中注明已核查的公共保护、替代实现及未确认条件。状态枚举以 `判定.md` 为准，不另加“代码路径确认”状态或置信度等级。

“审查覆盖”分别列需求追踪和审查项核对，后者包含适用的生命周期、公共机制、并发/事务/缓存项。每个已检查项需有证据和核对结果；缺材料的层写未审查范围，不据此推断无问题。未找到实现按 `判定.md` 分类，纯材料缺失不占 Bug 数量。

用例对照只是附加结果；需求明确而用例预期有误时，写未采用原因，不归为需求不明确。需求不明确单独统计，不冒充已确认或高概率 Bug。

不输出测试用例、测试计划、自动化脚本、单独的口径确认文件或其他附件。

没有发现问题时仍然输出报告，并明确写出审查范围和“当前资料范围内未发现有充分证据支持的 Bug”。
