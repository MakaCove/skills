# 清单格式

```markdown
# Bug 排查报告

## 审查范围
- 需求文档：
- 原型图：
- 项目：OMS / WMS / 本次指定的项目
- 前端代码：实际目录；分支、提交号及本地改动状态（可读取时）
- 后端代码：实际目录；分支、提交号及本地改动状态（可读取时）
- 数据库 MCP：可用 / 未提供
- 测试用例：有，写文件路径 / 本次无用例
- 审查限制：

## 审查覆盖

| 需求编号及摘要 | 页面/原型依据 | 前端位置 | 后端位置 | 数据库依据（已核查时） | 状态 | 核对结果或缺口 |
|---|---|---|---|---|---|---|

| 审查项及适用层 | 状态 | 已查位置或不适用原因 | 核对结果或关联问题 |
|---|---|---|---|

状态只能填写：已检查、本功能没有这一层、材料缺失、需要运行验证。
第二张表覆盖正文重点审查项和生命周期实际适用的层。已检查需写与预期一致或问题编号；同一需求不同层的状态不同时分行说明。没有数据库连接只影响数据库核查，不把已经检查的代码一并标为未审查。

## 未审查范围

| 范围 | 缺少的材料或条件 | 不能下的结论 |
|---|---|---|

## 总体结论
- 已确认 Bug：
- 高概率 Bug：
- 需要运行验证：
- 需求不明确：
- 当前未发现明显问题的模块：

## 已确认问题

### BUG-001 标题
- 严重程度：P0 / P1 / P2 / P3
- 结论：已确认 Bug
- 证据状态：需求和代码均明确 / 原型和代码明确 / 仅代码推导 / 仅数据库现象 / 需要运行验证
- 运行状态：未实际运行 / 已运行验证 / 部分运行验证
- 影响模块：
- 需求依据：
- 原型依据：
- 代码位置：
- 数据库依据：
- 触发条件：
- 推导或复现步骤：
- 预期行为：
- 当前代码行为：
- 影响范围：
- 根因分析：
- 已核查的公共保护机制及替代实现：
- 未确认条件：无 / 条件及其影响
- 受影响入口及用例编号（适用时）：
- 修复方向：
- 验证要求：

同一根因的多个入口写在这一条下面，不另起编号。

## 高概率问题

### BUG-002 标题
- 结论：高概率 Bug
- 证据状态：
- 运行状态：未实际运行
- 其余字段与已确认问题相同

## 需要运行验证

### BUG-003 标题
- 结论：需要运行验证
- 证据状态：需要运行验证
- 运行状态：未实际运行
- 验证依赖：数据库待确认
- 其余字段与已确认问题相同

没有数据库连接、又必须看库才能确认时，结论写“需要运行验证”，验证依赖写“数据库待确认”。

## 需求或原型不明确项

### 待确认规则及来源
- 结论：需求不明确
- 不明确的内容：
- 冲突来源或缺少的规则：
- 影响的需求、代码或用例：

需求不明确不计入已确认或高概率 Bug 数量；没有形成缺陷证据时不硬填严重程度、根因或运行状态。

## 数据库核查结果

未提供数据库连接时写“未提供，未核查”。提供时只写与本业务有关的只读结果，并区分样本现象、结构约束和根因推导。只读查询不代表页面或接口已经执行。

## 用例对照

没给用例时只写：本次无用例，按需求、原型和代码排查。

给了用例时填写：

| 用例编号 | 优先级 | 是否主流程或主要功能 | 对照结果 | 关联问题 | 说明 |
|---|---|---|---|---|---|

对照结果只能填：与代码路径一致、与代码路径不一致、用例预期有误未采用、预期待确认未采用、代码中未找到该场景。用例预期错误只在说明中指出，不自动写为需求不明确。

P0、P1，以及走主流程、覆盖主要业务功能的 P2、P3，必须出现在表里。未逐条对照的其余 P2、P3 在表下写明编号。

没找到场景时说明已搜索的入口和范围，按判定规则区分材料缺失、搜索尚未完成、确认未实现、外部依赖待验证。
```

没有实际运行时，运行状态写“未实际运行”，不把静态代码推导写成“已实际复现”。没有需求依据时，不把个人偏好或代码风格问题定性为 Bug。修复方向只写一句，不写补丁或 SQL。
