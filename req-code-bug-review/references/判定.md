# Bug 判定

## 已确认 Bug

只有在需求或原型给出明确预期，输入和入口可达，完整代码链路确定产生不同结果，并且相关公共校验、约束和替代实现已经核查时，才归类为“已确认 Bug”。不要求必须实际运行，但未运行时运行状态必须写“未实际运行”。保护配置未读到、代码版本不一致或关键条件未确认时，不能使用此结论。

## 高概率 Bug

已经有具体异常路径和影响证据，但仍依赖某个未确认的角色、数据、配置或运行条件时，归类为“高概率 Bug”。必须点名这个条件，以及它成立或不成立时结果如何变化。只有泛泛风险、没有触发路径时，不列为高概率 Bug。

## 需要运行验证

关键行为取决于外部服务、部署配置、真实数据库约束或运行时序，静态材料无法决定结果时，归类为“需要运行验证”，写清验证对象和所需证据。已能静态确定错误结果的，不仅因尚未运行就降为此类；技能本身不因这项分类自动获得运行接口或改数据的授权。

如果依赖数据库而没有数据库 MCP，在问题中写“验证依赖：数据库待确认”，但结论仍归类为“需要运行验证”。

## 需求不明确

需求和原型不足以判断正确行为时，归类为“需求不明确”，不要用个人习惯补全规则。

需求明确而用例写错时，只在“用例对照”说明未采用，不把它算作需求不明确或业务 Bug。需求和原型本身冲突时保留两者依据；用户已有明确补充只作用于其确认的规则，不自动推广到相邻规则。

## 未发现明显问题

只表示在当前提供的资料范围内没有发现有充分证据支持的问题，不等于证明系统绝对没有 Bug。

## “代码中未找到”的处理

搜索前先确认项目和版本。沿页面路由、请求路径、接口映射、服务调用、父类/公共组件、查询、任务及相关配置定位，记录搜索边界。

| 事实 | 如何处理 |
|---|---|
| 相关模块、依赖实现或配置未提供 | 审查状态写“材料缺失”，进入未审查范围；不因缺材料就创建一条 Bug |
| 只搜了关键词或还没追完调用链 | 继续搜索；资源或范围受限无法完成时记录未审查范围，不能宣布功能缺失 |
| 明确需求必须实现，相关入口和替代实现已核查，完整代码确定未实现 | 可确认为功能遗漏，给出需求、已查范围和实际缺失的行为；仅“搜不到名字”不构成证据 |
| 代码将行为委托给外部服务、插件或部署配置，结果尚不确定 | 有具体待核对行为时列“需要运行验证”，写清外部依赖；不能断言不存在实现 |

“代码中未找到”是搜索结果，不是第六种 Bug 结论。“材料缺失”是审查状态，也不占 Bug 数量。

## 三个字段的使用

- 结论：已确认 Bug、高概率 Bug、需要运行验证、需求不明确。前三类缺陷候选必须完整填写三个字段；需求不明确的规则项按模板单列，不硬填运行证据。
- 证据状态：需求和代码均明确、原型和代码明确、仅代码推导、仅数据库现象、需要运行验证。选择最能说明当前结论依据的一项，其他来源写入证据详情。
- 运行状态：未实际运行、已运行验证、部分运行验证。静态阅读始终是未实际运行；只做了只读数据库查询时，在数据库依据中记录查询范围，不能据此写页面或接口已运行验证。

“代码路径确认”可以用于解释推导过程，不是新的证据状态。仅数据库现象不能证明根因；仅代码推导不能替代缺失的业务预期。不新增置信度或第二套证据等级。

## 优化建议

业务结果符合明确需求，只是文案、交互步骤或性能不顺时，默认不写进报告。只有用户明确要求，才在报告末尾增加“优化建议”，并且不占用 Bug 编号。

修复方向只写一句高层处理方向，不写具体补丁、代码实现或 SQL。
