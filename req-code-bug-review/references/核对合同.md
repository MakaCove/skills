# 核对合同

先把每条需求和原型行为定位到代码，再下结论。

## 候选问题的定性门槛

1. **预期明确**：引用需求段落或原型节点；不把现有代码当作预期，不从某个角色名称自行推导数据归属规则。
2. **路径可达**：写清入口、允许的输入、前置状态和配置条件，排除未启用功能、不可达分支或已废弃实现。
3. **链路完整**：从调用入口追到实际处理结果，核查相关网关、拦截器、注解、切面、父类、公共服务、租户过滤和持久化约束。未拿到实现时写缺口，不写“没有校验”。
4. **因果成立**：说明哪条判断、哪个字段或哪段时序导致哪项错误结果，不能只贴片段或只用缺少某段代码证明结果。
5. **证据同版**：引用当前读取文件的相对路径和行号；区分前后端版本与数据库样本，部署版本未知时不把工作区推导当成线上事实。

全部满足才确认 Bug；缺少关键条件时按 `判定.md` 归类。不存在某个具体实现方式（如锁或事务注解），不等于不存在等效保护。

| 结论 | 使用条件 |
|---|---|
| 已确认 Bug | 预期明确，代码路径确定地产生错误结果 |
| 高概率 Bug | 风险明显，但依赖未确认条件 |
| 需要运行验证 | 静态资料无法确认，必须运行或查询环境 |
| 需求不明确 | 需求和原型不足以确定预期 |
| 未发现明显问题 | 当前资料范围内没有充分证据支持问题 |

“未发现明显问题”只用于已完成核对范围的总体说明，不单独建 Bug。

每个问题至少提供需求或原型依据、代码位置、触发条件、预期行为、当前代码行为和影响说明。只读代码时不得写成已经在环境中发生；没有数据库 MCP 时不得写成数据库已核查。

每项还需记录已核查的保护机制、替代实现和未确认条件。依据无法定位时注明缺口，不用虚构路径或行号补齐。

每条缺陷候选固定增加三列；需求不明确的规则项单列，不硬填严重程度和运行证据：

| 结论 | 证据状态 | 运行状态 |
|---|---|---|
| 已确认 Bug / 高概率 Bug / 需要运行验证 / 需求不明确 | 需求和代码均明确 / 原型和代码明确 / 仅代码推导 / 仅数据库现象 / 需要运行验证 | 未实际运行 / 已运行验证 / 部分运行验证 |

如果同一根因影响多个页面、接口或任务入口，只保留一个问题编号，并在问题中列出全部受影响入口。

审查覆盖按需求及实际适用的审查项分别记录，不能用“看过该模块”代替每项结果。状态只用“已检查”“本功能没有这一层”“材料缺失”“需要运行验证”；已检查还要说明与预期一致或关联哪个问题。

修复方向只写一句高层处理方向，不写补丁、具体代码或 SQL。

使用数据库 MCP 时：

- 不查询与当前业务无关的敏感数据。
- 不修改任何环境的数据。
- 一条样本只说明该样本的现象，不直接推论所有单据或记录都存在同样问题。
