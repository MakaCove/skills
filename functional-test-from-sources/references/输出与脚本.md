# 输出与脚本

## 单文件交付

只交付 `功能测试用例.xlsx`。输出目录优先使用用户指定值，未指定时读取 `config/projects.json` 对应项目的 output；不得混用其他项目。

固定六张表：测试说明 → 测试方法覆盖 → 测试场景 → 详细测试用例 → 需求覆盖 → 信息缺口。字段与取值见“用例格式.md”。

临时 Markdown、扫描 JSON、日志、执行记录不作为附件；边界与异常统一在详细用例，通过“类型”筛选。

## 交付检查

1. 人工将原始需求/验收清单逐项与用例断言核对，保留未覆盖、部分覆盖和待确认项。
2. 运行 `python scripts/validate_testcases.py "<功能测试用例.xlsx的实际路径>" --generation`；有错误先修正，再运行。
3. 检查方法是否实际运用、边界与组合是否遗漏、步骤是否可完成、预期是否有依据。结构校验不能替代这些判断。
4. 确认六表顺序、筛选/冻结表头、长文本换行及只交付一个文件。资料不足以设计任何用例时说明限制，不以空表宣布完成。

需要 Python 与 openpyxl；使用当前环境已有运行时。缺少依赖且无法运行时如实说明“校验未执行”及原因，不伪造通过结果。校验通过仅表示结构与引用符合规则，不证明需求理解正确、覆盖完整或业务执行通过。

## 脚本分工

| 脚本 | 职责与边界 |
|---|---|
| `analyze_codebase.py` | 静态接口定位与候选匹配；不执行项目、不证明接口存在/缺失，不生成完整业务覆盖结论 |
| `validate_testcases.py` | 校验六表字段、非空内容、编号、取值及方法/场景/需求与用例的引用；生成时必须加 `--generation` |
| `md_testcases_to_excel.py` | 可选兼容导出，搬运已整理完整的六表 Markdown；不自动推导需求、场景、方法适用性或覆盖状态，导出前后校验 |
| `testcase_io.py` | 共享字段、编号和取值定义；旧格式解析仅供遗留工具，不作为新用例契约 |
| `build_execution_template.py` | 遗留执行记录工具，不属于本技能默认流程，不作为交付步骤 |
| `test_quality_checks.py` | 维护脚本时的回归检查，不是为用户生成或执行业务测试 |

## 扫描使用

关注 `needs_review` 和 `review_notes`。动态路由、常量、网关前缀、封装默认方法、继承路由及无法解析的配置需读源代码确认。正则提取的权限/状态/异常信号只是附近文本的线索，不是该接口已执行这些校验的证据。

`matched_candidate` 只表示方法和候选路径匹配；`not_matched_in_scan` 只表示本次扫描未匹配，不代表后端缺失。读取失败或存在未识别路由时记录限制，不声称完整接口清单。

## 兼容导出输入

内部临时 Markdown 用 `## 工作表名称` 标明六个章节，每节一张与正式表头一致的表；信息缺口可以只有表头。必须提供独立整理的需求清单、场景与方法判断。可分文件输入，但最终六表内容必须完整且引用一致。

只有旧“功能点/链路”表或仅详细用例时，先人工补齐并转为上述六表；脚本拒绝用已有用例反推其他工作表。示例可作为写法参考，最终产物仍只有 Excel。
