# 覆盖合同

本文件负责确定覆盖范围、追踪关系和完成条件；工作表字段见“用例格式.md”。

## 先建立清单

设计用例之前，从原始需求和原型提取独立清单：需求编号、可验收规则、来源位置、适用条件、需观察的结果。将该清单作为“需求覆盖”的基础，不能从已生成用例反推需求列表。没有用例的需求仍保留；拆出的验收条件用 `AC-n`，在说明中记录父需求，不虚构规则。

仅代码出现、尚无明确正确预期的条件，作为补充对象挂到相关需求下并记录待确认；不得把当前实现包装成新的已确认需求。没有任何需求或原型依据时，明确说明预期不足，不靠编造编号满足校验。

## 补充覆盖对象

| 类型 | 编号 | 核对内容 |
|---|---|---|
| 需求与验收条件 | R-、AC- | 每条可验收规则及其适用条件 |
| 页面 | UI- | 入口、控件、默认值和可观察状态 |
| 接口 | API- | 参数、业务拒绝、响应和相关处理路径 |
| 分支 | BR- | 会改变结果的条件、拒绝原因和失败路径 |
| 权限 | PERM- | 资料中明确出现的允许、拒绝或数据归属 |
| 状态 | STATE- | 合法、非法、重复和终态操作 |
| 数据 | DATA- | 保存、修改、删除、关联和一致性 |

只列有依据、属于本次范围的对象。对象来源及去向写入场景的“覆盖说明”、用例“备注”或需求“说明”，不另建交付表。代码位置、原型节点、数据库检查点找到才填，不要求每项凑齐所有来源。

## 逐项反查

对原始清单中的每项核对：

1. 是否有对应场景、具体用例及来源。
2. 步骤是否实际触发该条件，预期是否断言该规则，而非仅在标题中提到。
3. 正常、拒绝、边界、重复操作及状态限制是否按适用性覆盖。
4. 未覆盖或预期待确认时，是否仍保留条目并说明原因、影响及缺少内容。

例如“提交成功”和“提交后禁止编辑”是不同断言，前者不能替代后者。P0、P1 的业务规则或场景集合应覆盖适用的成功与拒绝/失败结果，不要求单条用例同时成功又失败。

## 跨表关系

- 场景使用 `SC-001` 等编号。“覆盖说明”显式列举所含 `TC-nnn`，每条详细用例至少属于一个场景。
- 方法覆盖只引用实际使用该方法的用例；已使用的方法不能标“不适用”。
- 每条详细用例的 `R-n`/`AC-n` 都必须存在于需求覆盖；需求行的用例列表与详细用例关联双向一致。
- “已覆盖”要求全部适用断言已有用例；有用例但有漏项为“部分覆盖”；尚无用例为“未覆盖”；正确预期或适用性不明确为“待确认”。不能只因有一个用例就标“已覆盖”。
- 覆盖状态不能确定时写明原因。脚本只能核对结构与引用，不能替代上述语义判断。

## 统计与完成

材料完整性、测试设计覆盖、执行结果分开说明。若统计覆盖率，明确分母为本次独立识别的需求/验收条件数，分别列出已覆盖、部分覆盖、未覆盖、待确认数量；不能把部分覆盖算成全部覆盖，也不以用例数量充当覆盖率。

“测试设计已覆盖”仅适用于范围已说明、全部适用断言已核对且没有未解释缺口的情况。生成时所有用例仍为“未执行”，不得由设计覆盖推导业务通过或可以上线。
