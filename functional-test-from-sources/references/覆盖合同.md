# 覆盖合同

先列出可测试对象，再判断是否已经映射到用例。没有列出对象时，不声称“覆盖率 100%”。

## 覆盖对象

| 类型 | 编号 | 说明 |
|---|---|---|
| 需求 | R-、AC- | 一条可验收规则 |
| 页面 | UI- | 页面、控件或可观察页面状态 |
| 接口 | API- | 接口、关键参数和结果 |
| 分支 | BR- | 会改变结果的条件或失败路径 |
| 权限 | PERM- | 需求或代码明确出现的允许、拒绝或数据归属 |
| 状态 | STATE- | 合法、非法、重复或终态 |
| 数据 | DATA- | 会被保存、修改、删除或关联的数据 |

只有资料中实际出现的对象才列入；资料没有角色、权限或数据库规则时，不虚构对应对象。

## 覆盖判定

对象编号必须出现在需求来源、覆盖说明或备注中，并且步骤和预期结果真的检查了该对象。只写编号、不写断言不算覆盖。

- 核心正常流程至少一条
- 适用的拒绝、失败、边界和重复操作至少一条
- 接口场景适用时覆盖参数错误、业务拒绝和异常响应
- 状态场景适用时覆盖合法、非法和重复操作
- 数据场景适用时覆盖保存结果、修改结果和一致性

## 三套数字分开

- 材料完整性：需求、原型、前端、后端和数据库 MCP 是否提供
- 测试设计覆盖：已识别对象中有多少已经写入用例
- 执行结果：生成时为“未执行”；有执行记录后才写通过或失败

没有实际执行记录时，不写通过、失败或可以上线。
