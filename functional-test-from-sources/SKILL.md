# functional-test-from-sources

## 目标

本技能只负责生成一份功能测试用例文档，不负责排查 Bug、评价代码质量或提出代码修复方案。

最终输出一个文件：`功能测试用例.xlsx`。

## 可用输入

用户可以提供：

- 需求文档
- 原型图、页面截图或设计稿
- 前端代码
- 后端代码
- 数据库连接 MCP（可选，由用户手动提供）

不要求用户提供：用户角色说明、测试账号、接口文档、接口日志或运行日志。接口和参数信息应从前后端代码中提取。对于代码和资料中没有明确说明的内容，不要自行编造。

## 数据库 MCP 规则

- 先判断数据库 MCP 是否可用。
- 可用时，只读取完成测试设计所需的表结构、字段约束、关联关系和必要数据；不要执行删除、更新或其他破坏性操作。
- 不可用时继续生成测试用例；不要因为缺少 MCP 而停止，也不要虚构数据库表名、字段名或查询结果。
- 数据库无法确认的检查点写入“信息缺口”，并标记为“需要数据库或接口验证”。

## 分析流程

1. 从需求中提取功能目标、业务规则、字段规则、状态变化、成功条件和失败条件。
2. 从原型中提取页面、入口、字段、按钮、弹窗、默认状态、禁用状态、空数据状态和跳转关系。
3. 从前端代码中提取页面行为、表单校验、请求参数、响应处理和错误展示。
4. 从后端代码中提取接口入口、参数校验、业务规则、权限条件、状态变化和异常处理。
5. 如果数据库 MCP 可用，补充数据准备条件、数据库检查点和数据一致性检查。
6. 设计正常、异常、边界、权限、状态和数据一致性场景。
7. 生成一份可直接执行的测试用例文件。

## 必须覆盖的场景

- 核心正常流程
- 必填、格式、长度和数值边界
- 空数据、重复数据和非法数据
- 需求或代码中存在对应路径时的接口失败、网络异常和超时
- 重复点击和重复提交
- 页面刷新、返回、取消和重新进入
- 新增、编辑、删除、撤销和状态切换
- 分页、筛选、排序和搜索
- 需求或代码中明确出现的角色、权限和数据归属
- 前端、接口和数据库结果的一致性

只有需求、原型或代码中确实存在对应处理路径时，才生成接口失败、网络异常、超时、重试或异步失败用例。没有依据时写入“信息缺口”，不自行创造路径。

## 基础八大用例设计方法

生成测试用例时，读取 `references/测试方法.md` 和 `references/判定.md`，根据适用性选择八大方法，并在每条用例中填写“设计方法”：

1. **等价类**：把输入或业务条件划分为有效类和无效类，每个适用类至少覆盖一条。
2. **边界值**：覆盖最小值、最大值、刚好越界值和空值等边界；没有明确边界时不虚构数值。
3. **判定表**：多个条件共同决定结果时，列出条件组合和对应结果；结果不同的组合不能合并。
4. **因果图**：多个输入原因经过逻辑关系影响结果时，先梳理原因、约束和结果，再转成可执行用例。
5. **状态迁移**：存在状态字段或生命周期时，覆盖合法迁移、非法迁移、重复操作和终态操作。
6. **场景法**：覆盖用户主流程、替代流程、异常流程和跨页面业务流程。
7. **正交或成对组合**：多个独立选项组合数量很大时，用最少组合覆盖主要交互；必须说明选择的组合和省略理由。
8. **错误推测**：根据代码、业务风险和常见故障补充重复提交、空响应、超时、权限绕过、数据不一致等用例。

不要求每种方法都生成用例。`测试方法覆盖` 固定 8 行，顺序和名称只能是：等价类、边界值、判定表、因果图、状态迁移、场景法、正交或成对组合、错误推测。适用性只能填写“适用”“不适用”或“适用但未覆盖”之一；适用时填写用例编号，不适用时在“说明”中填写原因，适用但未覆盖时在“说明”中填写缺少的场景。详细用例的“设计方法”填写其中一种，或用加号组合，例如“等价类 + 场景法”。不能写“等价类划分”“边界值分析”“场景法 / 用例法”，也不能只写“异常测试”。

如果需求没有定义某类权限或角色，不要虚构角色测试；将缺少的规则写入“信息缺口”。

## 用例要求

每条用例必须包含：

- 用例编号
- 设计方法
- 所属模块
- 用例标题
- 优先级
- 关联需求
- 前置条件
- 测试数据
- 可执行的操作步骤
- 页面预期结果
- 接口或数据预期结果（适用时）
- 数据库验证：只能填“需要”或“不需要”，不能空着
- 备注或信息缺口

关联需求必须带 `R-n` 或 `AC-n`，不能空着。生成时执行结果填“未执行”；有真实执行记录后可以改成通过或失败。

前置条件应尽量写成四类信息：需要准备的数据、数据应处于的状态、操作后观察页面/接口/数据库的结果、是否依赖数据库 MCP。没有账号或现成数据时，不编造账号和数据编号，写准备条件和信息缺口。

预期结果必须具体可判断，不能使用“系统正常”“页面无误”等模糊表述。当前代码行为不能自动作为正确预期；预期优先依据明确需求和原型，代码用于补充实际测试条件。

优先级规则：P0 为核心流程、数据保存、权限和关键状态；P1 为重要异常和边界；P2 为一般功能和提示；P3 为低风险体验问题。

## 输出文件

只输出一个 `功能测试用例.xlsx`，包含以下工作表：

1. `测试说明`：测试范围、输入来源、数据库 MCP 是否可用、限制条件。
2. `测试方法覆盖`：八大方法的适用性、对应案例和说明。
3. `测试场景`：场景编号、场景名称、优先级、关联需求。
4. `详细测试用例`：正常、边界、异常和失败场景的完整可执行用例。
5. `需求覆盖`：需求与用例的对应关系。
6. `信息缺口`：缺少资料、影响范围和需要补充的内容。

不要额外输出 Bug 报告、代码修复建议、测试脚本或其他附件。边界和异常通过“类型”筛选，不建立第二张用例表。

## 需求、原型和代码冲突

如果三者存在差异：分别记录需求表现、原型表现和当前代码表现；不要自行选择当前代码作为正确答案；将差异写入“信息缺口”，并在相关用例中说明待确认的预期。
