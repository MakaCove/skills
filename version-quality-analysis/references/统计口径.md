# 统计口径

负责范围、时间、记录归并和计数；验证程度、代码关系及质量等级由其他文件负责。

## 范围与时点

记录目标需求/版本、初始发布日期、改动模块、统计截止时间及线上观察起止时间。分析当天只是报告日期，不能自动当作缺陷数据截止时间。未提供时写“未知”，不编造观察天数。

核对缺陷所属版本与模块。明确不属于本版的记录列为范围外，并给出排除依据；归属不明的记录单列“版本归属待确认”，不强计入本版，也不视为已证明无关。前端、后端与热修复版本分别记，不能把后续修复结果回填为初始发布状态。

区分“列表未提供”“明确提供零缺陷”“所给列表无线上记录但收集范围未知”。第三种只说明该列表未记录到，不说明线上没有问题。发现阶段依据首次发现时间或明确阶段记录；补录时间不等于首次发现时间，发布后记录也不自动等于生产环境问题。

## 内部整理字段

逐条保留来源位置或行号、原始编号、标题、版本归属、模块、发现来源、首次发现阶段/时间、环境、有效性、原始与归一状态、严重程度、关闭原因、修复及验证证据。字段未提供就标注缺失，不为每条强造完整信息。

- 发现来源：研发自测、测试提交、代码排查、其他、未提供。保留原始文本，无法判断归“其他/未提供”并解释。
- 发现阶段：发布前、发布后、未确认。发现来源不能决定阶段。
- 有效性：已确认真实缺陷、待确认、误报、无法判定。可依据用户明确说明的有效缺陷范围、确认记录或列表标注；仅有“已关闭”不能排除误报或重复关闭。
- 处理状态：待确认、修复中、待验证、已关闭、状态无法归类。只按有依据的流程含义映射；“修复完成/已解决”不能自动映射为验证通过。
- 严重程度：沿用原始等级及项目已有定义，不擅自把不同项目的 P0、严重、S1 互相换算。缺失单列“未提供”。

例如“排查确认的真实缺陷”可以支持发现来源与有效性；“线上补录”首先是原始渠道信息，仍要核对首次发现阶段与发现方，不能一条记录重复算进多个来源。

## 去重与历史状态

1. 同一来源系统/项目的相同缺陷编号归为同一张单；编号跨系统冲突时保留来源，不误合并。
2. 同编号多条更新或状态历史采用截止时点前最后一条明确记录；冲突无法排序时标“状态无法归类”，说明冲突。
3. 只有截止时点后的快照时，不能用它代替截止时状态；无法还原则状态未知。缺陷发现时间明确在截止后时不计入当期，另注后续信息。
4. 不同编号只有明确重复关系或可靠身份依据时才能按同一缺陷去重，并保留全部编号。仅同标题、同模块或同现象不够。
5. 没有编号时用“原列表第 n 行”等定位，不伪造系统编号。无法排除重复时说明“按可区分记录计数，唯一缺陷数尚不能确认”。
6. 同根因的不同缺陷单可以归为一组，但不减少缺陷单数量。根因未确认时只做模块/现象分组。

## 计数基数与核对

先说明原始记录数、历史/重复归并情况、去重后记录数、范围外及归属待确认数量。本版纳入数 S = 已确认真实缺陷 C + 待确认 P + 误报 F + 有效性无法判定 U；范围外与归属待确认不包含在 S。

来源、发现阶段、严重程度、处理状态的分布默认都以 C 为基数，缺失/无法归类必须保留，分别求和应等于 C。待确认、误报、无法判定另列，不混入已确认真实缺陷分布或真实缺陷率。确需展示所有记录时另标基数，不能在同一表中混用。

- 有依据的发布前真实缺陷数 + 发布后真实缺陷数 + 阶段未确认真实缺陷数 = C。
- 误报不算遗留缺陷；待确认项单列“待确认风险”，不能写成已确认遗留缺陷。
- C 中未关闭项按状态列出；状态不明单列，不能计为已关闭或假定已修复。
- 已关闭但原因是延期、不修复、风险接受等，仍保留列表状态，并单独说明未消除的业务风险，不把关闭数当修复通过数。
- 缺陷单数不与根因组数混算；跨多模块的同一缺陷单只计一次，另列受影响模块，避免分组求和虚增。

没有明确分母时不计算比例。线上记录不完整、观察期不明、不同版本范围不同或唯一数量存疑时，不用数量差异直接推断质量升降或测试不足。统计是材料范围内的结果，不保证所有实际缺陷都已被收集。
