# version-quality-analysis

## 目标与交付

独立分析已经发布的指定版本，只输出一个 `业务名-版本质量分析-YYYYMMDD.md`。业务名取实际需求名或版本号，日期取分析当天，文件名中的非法字符替换为短横线。

报告固定六部分：版本范围、缺陷数量、验证程度、具体缺陷、发布后代码质量、结论。分析已有材料，不重新排查新 Bug、不默认执行页面/接口测试、不修改代码、不做发布准入决定，也不要求先运行其他技能。改进项只说明下次需补的验证范围或分析材料，不生成具体测试用例、修复补丁或额外附件。

## 输入与缺失处理

基础材料：

- 版本号或需求名、发布日期、是否测试介入、改动模块。缺某项时如实标“材料缺失”，其余分析继续；尚未发布的版本不适用本技能。
- 缺陷列表及其范围。明确提供“本范围零缺陷”属于有效输入；未提供列表不等于零缺陷。
- 本次改过的代码：仅改前端或后端时提供对应一端即可；两端都改则分别核对，缺失一端写明不能核对的范围。热修复与初始发布代码分开。

有就用、没有不索要或编造：用例执行记录、验收标准、质量标准、缺陷历史记录、发布基线/标签及热修复版本。没有这些材料不编造执行率、覆盖率、发布时间或代码版本。

未提供缺陷列表，也未明确零缺陷，或完全没有可审阅的本版改动代码时，说明缺什么，停止生成报告。其余缺口写进报告并限制判断；不能为凑评级补造事实。

## 工作流程

| 阶段 | 读取文件 | 完成内容 |
|---|---|---|
| 确定范围并统计 | [统计口径.md](references/统计口径.md) | 明确版本、统计截止时间、线上观察期、列表范围；逐条去重，保留未知项，核对计数 |
| 核对验证与代码 | [验证与代码核对.md](references/验证与代码核对.md) | 分别核对测试执行、核心流程、缺陷处理；追踪已有缺陷与发布/热修复代码的关系 |
| 作出判断 | [结论判定.md](references/结论判定.md) | 根据业务影响、标准、验证证据和遗留项判断；证据不足时暂不评级 |
| 形成报告 | [报告格式.md](references/报告格式.md) | 按六部分写入一个文件，完成交付核对；需要具体写法时读 [示例.md](references/示例.md) |

先固定分析范围和数据时点，再统计、核对与判断。代码只读本版改动、热修复及理解这些路径必需的直接上下文；没有整仓时不扩展搜查无关目录。代码未注明对应发布版本时保留版本限制，不默认当前分支就是线上版本。

## 核心边界

- 发现来源、发布前后阶段、有效性、处理状态分别记录，不能互相推断。
- 缺陷单数量与根因分组数量分开；同根因归纳不改变原缺陷单数量。
- 测试执行、缺陷关闭、修复验证分开；“已关闭”本身不能证明修复通过或功能已全面测试。
- 没有测试人员介入，不自动写成“研发自测完成”；没有执行记录写“未提供”。
- 同模块同类型只支持同类问题再次出现；复发或修复未生效需要进一步证据。
- 静态路径对应不能写成线上已复现或修复已成功；未对应到代码不能认定与本版无关。
- 不以缺陷数量多少直接决定等级。质量等级保留“可接受 / 有遗留风险 / 质量不达标”；证据不足时写“暂不评级（证据不足）”，这是未作评级，不是第四个等级。
- 所有计数和判断注明依据。资料未给的严重程度、状态、执行结果和阈值不得自行补齐。

交付前按报告格式核对计数、版本/时间、证据引用和结论一致性。当前不设统计脚本；手工核对与结构检查不能声称已经完成业务测试。
