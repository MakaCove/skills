# 主流程识别与编排（UI）

## 目标

将 `project-analysis` 中的主流程候选、页面入口线索、业务流程说明转为 `mainFlowInventory`，并编排用例执行顺序与依赖。

---

## 1. 输入

| 输入 | 来源 | 用途 |
|------|------|------|
| `mainFlowCandidates[]` | project-analysis | 预标注候选 |
| `chainHints.candidateChains[]` | project-analysis | 业务链路说明（尤其是 `note` 字段） |
| `crossModuleRefs[]` | project-analysis | 跨模块外键依赖 |
| 用户变更文档 | 用户对话中提供 | 本次变更范围 |
| [可选] 需求文档 / 原型图 | 用户可能提供 | 验收标准 |
| 前端组件源码 | Agent 自行读取 `.vue/.tsx/.jsx` | 确认页面性质和操作入口 |

---

## 2. 6 条识别规则

### 规则 1：读 chainHints 理解业务流程关系

遍历 `chainHints.candidateChains[]`，读取每条链路的 `note` 字段理解业务语义。调用 `crossModuleRefs[]` 确认跨模块数据依赖。

判断 candidate 之间的关系：

| 关系类型 | 特征 | 处理方式 |
|----------|------|----------|
| **串联** | A 操作的结果触发 B 操作（如 A 新增数据 → B 引用该数据做下一步） | 保留各自独立 flow，B 的 `dependsOn` 指向 A |
| **依赖** | B 需要 A 产出的数据（如 B 的下拉选项来自 A 模块） | B 保留独立 flow，`consumes` A 的产出变量 |
| **独立** | 无上下游关联 | 各自独立 flow |

**不可简单地将多个 candidate 合并为一条 flow**，合并会丢失子用例拆分粒度。优先保留独立 flow 并用 `dependsOn` 表达关系。

### 规则 2：读 confidence 决定展开策略

`mainFlowCandidates[].confidence` 从 project-analyzer 阶段标注，决定展开强度：

| confidence | 含义 | 策略 |
|------------|------|------|
| `high` | 双重验证（chainHints + 源码） | 确定展开，主流程保留，深度覆盖 |
| `medium` | 仅源码归纳 | 展开但标注"待确认"，只生成冒烟级用例 |
| `low` | 推测性 | 仅在变更文档明确提到该 candidate 时才展开，且仅冒烟 |

### 规则 3：变更文档收窄范围

`mainFlowCandidates` 是 project-analyzer 全量扫描的结果，但本次只需要覆盖变更相关内容：

- 变更文档提到的 candidate → **深度展开**，每条操作至少 3 条子用例
- 变更文档未提到但 chainHints 显示有依赖 → **关联冒烟**，1 条用例
- 其余 → **回归覆盖**，1 条用例，标记 `scope: "regression"`

从变更文档中提取："xxx页面/模块/功能"的文本 → 匹配 project-analysis 中的 pageEntryHints.label、navigationTree.label、mainFlowCandidates.name → 判定为核心变更。

### 规则 4：排除必须写理由

任何没有出现在最终 `mainFlowInventory` 中的 candidate，必须输出一条 `exclusionReason` 明确说明丢弃原因。禁止无声丢弃。

`exclusionReason` 示例：
- `"该 candidate 对应的页面不在本次变更范围内，标记为回归覆盖"`
- `"该 candidate 的 confidence 为 low 且变更文档未提及"`
- `"该 candidate 为纯查询页面，无交互操作，合并到关联冒烟"`

### 规则 5：打开组件源码确认页面性质

对每条 candidate 涉及的页面，必须打开组件源码确认：

- 这是一个独立路由页面、弹窗子组件、还是 Tab 页签？
- 页面内有哪些功能操作入口？（决定子用例的 action 类型：工具栏按钮 / 行操作 / 页内按钮）
- 操作后的页面跳转或状态变化？（决定断言：跳回列表 / 刷新当前页 / 弹窗关闭）
- 是否有条件渲染的操作按钮？（如只有特定状态下才出现的"审核"按钮）

### 规则 6：FLOW ID 命名规范

```
FLOW-{MODULE}-{序号}          通用格式，如 FLOW-ORDERS-001
若有多个 CRUD 操作拆分：
  FLOW-{MODULE}-{序号}-LIST    列表查询
  FLOW-{MODULE}-{序号}-DETAIL  详情查看
  FLOW-{MODULE}-{序号}-ADD     新增创建
  FLOW-{MODULE}-{序号}-UPDATE  编辑修改
  FLOW-{MODULE}-{序号}-DELETE  删除
  FLOW-{MODULE}-{序号}-ACTION  状态流转/关键操作（审批、提交、导出）
```

## 3. mainFlowInventory 条目结构

```json
{
  "id": "FLOW-{MODULE}-{序号}[-后缀]",
  "name": "中文流程描述",
  "module": "模块名（小写英文）",
  "priority": "P0/P1/P2",
  "userGoal": "用户在这个流程中的目标",
  "menuPath": ["一级菜单", "二级菜单"],
  "stepsSummary": "操作步骤一句话总结",
  "evidence": ["组件文件: 关键行"],
  "suggestedCaseIds": ["TC-UI-{MODULE}-{序号}", ...],
  "chainVars": ["变量1"],
  "confidence": "high/medium/low",
  "scope": "core/related/regression",
  "exclusionReason": null
}
```

`exclusionReason` 仅当 candidate 不在 mainFlowInventory 中时填写该 candidate 的排除原因。

---

## 4. scope 字段与执行层级

每条用例必须标注 `scope` 字段，影响执行层级和依赖策略：

| scope | 定义 | executionTier 规则 | 依赖 |
|-------|------|---------------------|------|
| `core` | 本次变更直接涉及的页面/功能 | 按操作类型分配 tier（4-80） | 可跨 scope 依赖 |
| `related` | 核心变更的上下游依赖页面 | 固定 `30` | 可依赖 core 用例的变量 |
| `regression` | 未变更页面的回归覆盖 | 固定 `100` | 不依赖任何变量（自包含） |

---

## 5. 用例类型约束（硬规则）

- 允许：`TC-UI-AUTH-*` + `TC-UI-{MODULE}-{序号}`
- **允许**：校验失败专项（须挂接到主流程，使用 `FLOW-{MODULE}-{序号}-VALIDATION` 子流程 id）
- **允许**：取消操作专项（须挂接到主流程，使用 `FLOW-{MODULE}-{序号}-CANCEL` 子流程 id）
- **允许**：表格交互专项（分页/筛选/排序，须挂接到主流程）
- 禁止：纯打开页面专项（无任何交互操作仅导航到页面）
- 每条用例必须有 `trace.flowRefs`，且能映射到 `mainFlowInventory` 的 `FLOW-*`

### 5.1 主流程子用例拆分规则

每条主流程应拆分为多条子用例覆盖不同场景。**不可只用一条 happy path 用例覆盖全部**。

```text
FLOW-ORDERS-001 创建订单
  ├── TC-UI-ORDERS-001  正向创建：完整填写所有字段 → 提交 → toast 提示 + 列表可见
  ├── TC-UI-ORDERS-002  必填校验：所有必填字段为空 → 提交 → 字段级错误提示
  ├── TC-UI-ORDERS-003  取消操作：填写部分字段 → 取消 → 弹窗关闭 + 列表不变
  └── TC-UI-ORDERS-004  边界输入：非法字符/超长文本 → 提交 → 格式校验提示
```

计为不同的 `FLOW-*-SUB`，所有子用例的 `flowRefs` 都指向同一条主流程 `FLOW-*`。

## 6. 生命周期依赖规则（CRUD 强制依赖）

当 mainFlowInventory 中存在同一模块的 CRUD 子流程时，必须建立以下依赖：

| 用例类型 | executionTier | dependsOn | 说明 |
|----------|---------------|-----------|------|
| 列表查询(LIST) | 3 | — | 最基础，无上依赖 |
| 详情查看(DETAIL) | 3 | — | 可独立（通过列表进入），也可依赖创建 |
| 创建(ADD) | 4 | — | 可独立 |
| 编辑(UPDATE) | 5 | 依赖 ADD（创建的数据） | **必须**依赖创建用例的 saveAs 变量 |
| 删除(DELETE) | 80 | 依赖 ADD（创建的数据） | **必须**依赖创建用例的 saveAs 变量 |
| 状态流转(ACTION) | 60 | 依赖 ADD（创建的数据） | **必须**依赖创建用例的 saveAs 变量 |

### 6.1 依赖链示例

```text
TC-UI-ORDERS-001 (ADD) —— produces: ["orderName", "orderId"]
    ├── TC-UI-ORDERS-002 (ADD-VALIDATION) —— 同 flow，无依赖
    ├── TC-UI-ORDERS-003 (ADD-CANCEL) —— 同 flow，无依赖
    ├── TC-UI-ORDERS-004 (UPDATE) —— dependsOn: [TC-UI-ORDERS-001], consumes: ["orderName"]
    └── TC-UI-ORDERS-005 (DELETE) —— dependsOn: [TC-UI-ORDERS-001], consumes: ["orderId"]
```

## 7. 变量与依赖补全

### 7.1 变量分类

| 类型 | 示例 | 依赖策略 |
|------|------|----------|
| 系统变量 | `username` `password` `timestamp` | 不建立 dependsOn |
| 会话变量 | `sessionUser` | 来自登录用例 |
| 业务变量 | `orderTitle` `projectName` | 来自上游用例的 `saveAs/trace.produces` |

### 7.2 生产者识别

- 登录用例：`trace.produces: ["sessionUser"]`
- 主流程创建/选择步骤：`saveAs` 或 `trace.produces`

### 7.3 消费者补全

扫描步骤 `value/target/useVar` 中 `{{var}}`：

- 有生产者则补 `trace.dependsOn` + `trace.consumes`
- 除登录用例外，业务用例默认依赖登录用例，并以 `ensure_session` 开头

### 7.4 scope 对依赖的限制

| scope | 跨 scope 依赖 |
|-------|---------------|
| `core` | 可依赖任意 scope 的用例 |
| `related` | 只能依赖 `core` scope 的用例 |
| `regression` | 不依赖任何用例（自包含），只依赖登录 |

---

## 8. executionTier 完整规则

| tier | scope | 含义 |
|------|-------|------|
| 0 | core | `login-bootstrap` |
| 3 | core/related/regression | `resource-read`（列表查询、详情查看） |
| 4 | core | `resource-create`（新增、创建） |
| 5 | core | `resource-update`（编辑、修改） |
| 30 | related | 关联冒烟（固定） |
| 60 | core | `resource-action`（状态流转、审批、提交） |
| 80 | core | `resource-delete`（删除、销毁） |
| 90 | core | `auth-destructive`（登出、改密） |
| 100 | regression | 回归覆盖（固定） |

---

## 9. 拓扑排序

1. `trace.dependsOn` 建图
2. 先按 `executionTier`，再拓扑排序
3. 写 `executionOrder: 1..N`
4. 按 `executionOrder` 重排数组

## 10. 输出字段

- 用例级（trace 内）：`trace.dependsOn`、`trace.produces`、`trace.consumes`
- 用例级（根级）：`executionTier`、`executionOrder`、`scope`
- 步骤级：`saveAs` / `useVar`

## 11. 验收清单

**主流程识别：**
- [ ] 每条变更文档提到的 candidate 都出现在 mainFlowInventory 中（核心变更）
- [ ] 每条核心变更 flow 的 suggestedCaseIds 至少包含 3 条用例 ID
- [ ] 所有 candidate 都有归属（在 mainFlowInventory 中或有 exclusionReason）
- [ ] 所有 `chainHints.candidateChains[].note` 已被读取，业务关系已理解
- [ ] 所有 `confidence: "high"` 的 candidate 已展开
- [ ] FLOW ID 符合命名规范
- [ ] 无纯打开页面 flow（每条 flow 至少有用户操作目标）

**编排：**
- [ ] 所有用例都有 `scope` 字段（core / related / regression）
- [ ] 登录用例最前（tier 0）；业务用例不重复完整登录
- [ ] 同一模块的编辑/删除用例依赖创建用例
- [ ] 业务变量消费有上游生产者，且依赖在 scope 规则内
- [ ] 业务页入口走 `click_menu`（守卫专项除外）
- [ ] 每条主流程至少包含 3 条子用例（正向 + 必填校验 + 取消/编辑）
- [ ] 无纯打开页面用例（仅导航无交互操作）
- [ ] 校验失败/取消子用例使用子 flowRefs 追溯到主流程

---

## 12. 反模式

- 每条用例都写完整登录流程
- 用 `navigate` 直链业务页替代菜单操作
- 使用 `{{projectName}}` 却无 `trace.dependsOn` / `trace.consumes`
- 一条主流程只生成一条 happy path 用例（缺少负向/边界/交互分支）
- 创建类用例只填一个字段（必须覆盖所有必填字段）
- 断言只有 URL 检查不验证数据正确性
- 编辑/删除用例不依赖创建用例（无生命周期依赖）
- regression 用例尝试消费 core 变量
