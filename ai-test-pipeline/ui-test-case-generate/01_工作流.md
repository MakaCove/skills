# 工作流（UI 用例生成）

## 输入

**必选输入**：
1. `ai-tests/test-artifacts/project-analysis-*.json` — 全量代码索引（navigationTree、pageEntryHints、mainFlowCandidates、chainHints、auth）
2. **用户变更文档** — 用户在对话中提供，说明本次变更范围（改了哪些页面/模块、新增了什么功能、修复了什么 Bug）

**可选输入**：
3. **需求文档 / 原型图** — 用户可能提供，含验收标准
4. **核心变更页面的组件源码** — Agent 自行从项目中读取 `.vue` / `.tsx` / `.jsx` 文件

---

## 执行步骤

```
- [ ] 1. 读取 project-analysis
- [ ] 2. 读取用户变更文档 → 圈定测试范围（核心变更 / 关联冒烟 / 回归覆盖）
- [ ] 3. [可选] 读取需求文档 / 原型图 → 提取验收标准 → 映射断言
- [ ] 4. 对核心变更页面 → 打开组件源码提取可操作元素
- [ ] 5. 从 navigationTree 解析导航路径
- [ ] 6. 生成 UI 用例 JSON → 写入 ai-tests/test-artifacts/ui-cases/
- [ ] 7. 校验确认
```

输出目录：`ai-tests/test-artifacts/ui-cases/`
Schema 见 [shared/05_UI用例结构.md](../shared/05_UI用例结构.md)。

---

## 步骤 2：圈定测试范围

从用户变更文档中提取本次变更涉及的范围，按以下规则分级：

### 2.1 三级范围

| 范围级别 | 定义 | 如何识别 | 用例深度 |
|----------|------|----------|----------|
| **核心变更** | 变更文档中明确提到的新增/修改/重构页面 | 变更文档列出的页面名、路由、功能名 | 深度覆盖：每条操作至少 3 条子用例（正向 + 校验 + 取消） |
| **关联冒烟** | 核心变更页面的上下游依赖页面 | 从 `chainHints` 和 `crossModuleRefs` 推断 | 1 条冒烟用例（菜单进入 + 基本可见 + 关键列断言） |
| **回归覆盖** | project-analysis 中其余未变更页面 | 排除核心和关联后的剩余主流程候选 | 1 条最简用例（菜单进入 + URL 断言），标记 `scope: "regression"` |

### 2.2 产出：测试范围清单

步骤 2 完成后必须输出一份范围清单：

```text
核心变更（深度覆盖，≥3 条用例/操作）:
  - <页面1名称>：<变更类型>，涉及操作：[新建, 编辑, 删除]
  - <页面2名称>：<变更类型>，涉及操作：[...]

关联冒烟（1 条/页面）:
  - <关联页面1>：依赖关系说明
  - <关联页面2>：依赖关系说明

回归覆盖（1 条/页面）:
  - <页面A>
  - <页面B>
  - ...
```

## 步骤 3 [可选]：读取需求文档/原型图 → 提取断言

### 3.1 若用户提供了需求文档或原型图

逐条提取验收标准，映射为 assertions：

| 验收标准类型 | 映射为断言 | 示例 |
|-------------|-----------|------|
| "应显示 XXX" | `element_visible` | `{ "type": "element_visible", "target": "XXX", "expected": true }` |
| "应包含 XXX" | `text_contains` | `{ "type": "text_contains", "target": "XXX", "expected": true }` |
| "成功后跳转到 XXX" | `url_contains` | `{ "type": "url_contains", "target": "XXX", "expected": true }` |
| "校验不通过提示" | `text_contains` + `dialog_visible` | `{ "type": "text_contains", "target": "必填", "expected": true }` |
| "弹窗关闭/页面刷新" | `dialog_hidden` / `element_hidden` | `{ "type": "dialog_hidden", "expected": true }` |

验收标准缺失时（如需求文档只描述了正向流程没写校验规则），使用步骤 3.2 的通用规则补全。

### 3.2 若用户未提供需求文档或原型图（回退：通用断言规则）

不猜测具体业务字段和文案，只断言操作的基本预期结果：

| 用例类型 | 通用断言 |
|----------|----------|
| 创建/新增 | `text_contains`：页面出现"成功"类提示词；`url_contains`：跳回到列表页或停留在合理路由；`text_contains`：用 `saveAs` 变量值（如 `AUTO-` 前缀）验证新数据可见 |
| 编辑/修改 | `text_contains`：页面出现"成功"/"保存"类提示词；`text_contains`：更新后的值可见（用 `saveAs` 变量值） |
| 必填校验 | `dialog_visible`：弹窗或表单仍然打开；`text_contains`：出现"必填"/"不能为空"/"请选择"/"请填写"等错误提示；`element_visible`：提交按钮仍可见（未提交出去） |
| 取消操作 | `dialog_hidden` / `element_hidden`：弹窗或表单已关闭；`text_not_contains`：填入的测试数据未出现在列表中 |
| 列表查询 | `url_contains`：当前路由正确；`text_contains`：关键列名或页面标题可见；`count_gte`：至少存在 N 条记录（N ≥ 1） |
| 删除操作 | `text_contains`："删除成功"/"成功"类提示词；`text_not_contains`：被删除项不在列表中 |
| 状态流转 | `text_contains`：目标状态的文案；`text_contains`："操作成功"/"成功"类提示词；`element_visible`：新状态下可用的操作按钮 |

### 3.3 产出

每条主流程标注：断言来源（`需求文档` 或 `通用规则`）和对应的 assertions 模板。

## 步骤 4：逐页拆解（仅核心变更页面）

**仅对步骤 2 圈定的核心变更页面进行深度拆解。** 关联冒烟和回归覆盖页面跳过此步骤。

### 4.1 信息源读取

对每个核心变更页面：

1. 优先从 `project-analysis.pageEntryHints.detail` 或 `navigationTree[leaf].detail` 读取
2. 如果 `detail` 缺失或不完整 → **必须打开对应的前端组件文件**（`.vue` / `.tsx` / `.jsx`），自行提取：
   - 弹窗标题（dialog/modal/drawer title）
   - 表单字段（label + placeholder + 是否必填 + 控件类型）
   - 操作按钮（提交 / 取消 / 保存 / 编辑 / 删除等）
   - 列表表格列名 + 行内操作
   - Tab 页签结构

### 4.2 产出：可操作元素清单

对每个核心变更页面整理出结构化清单：

```text
页面：/{路由路径}（{页面名称}）
  ├── 操作入口：{按钮在工具栏/行操作的说明}
  ├── 弹窗 "{弹窗标题}"
  │   ├── {字段1名称}（select, placeholder={placeholder}, 必填）
  │   ├── {字段2名称}（text, placeholder={placeholder}, 必填）
  │   ├── ...
  │   ├── [提交] 按钮
  │   └── [取消] 按钮
  └── 列表表格（如适用）
      ├── 列：{列名1} | {列名2} | ...
      ├── 行操作：{操作列表}
      └── 工具栏：{按钮列表}
```

### 4.3 组件文件定位

按以下优先级：
1. `project-analysis.downstream.uiTestCaseGenerate.readPaths` 指定路径
2. 前端路由 `component` 字段指向的文件
3. Glob 搜索 `**/views/**/*.vue` / `**/pages/**/*.tsx`

打开后重点读取 `<template>`（Vue）或 JSX 返回值（React）。

## 步骤 5：解析导航路径并生成 routeMenuMap

从 `project-analysis.navigationTree` 中查找每个页面的完整菜单导航路径，填入 `coverage.routeMenuMap`。

### 5.1 路径格式

`routeMenuMap` 中每条记录的 `menuGroup` 为父级菜单分组名，`menuLabel` 为叶子页面文案：

```json
// 多层级菜单 "货品 > 品牌信息"
{ "route": "/brand", "menuLabel": "品牌信息", "menuGroup": "货品", "requiresAuth": true }
// 单层级菜单 "仪表盘"
{ "route": "/dashboard", "menuLabel": "仪表盘", "menuGroup": null, "requiresAuth": true }
```

### 5.2 与用例步骤的关系

**用例只生成一步 `click_menu`，target 指向 `menuLabel`（叶子页面），不生成父级步骤**。执行器通过 `menuGroup` 自动展开父级菜单：

```
用例步骤:                  click_menu("品牌信息")
                                ↓
routeMenuMap:             { menuLabel: "品牌信息", menuGroup: "货品" }
                                ↓
执行器自动执行:            hover("货品") → click(.last-menu-item[title="品牌信息"])
```

**不要生成**: `click_menu("货品")` → `click_menu("品牌信息")`。多余的父级步骤会导致执行器在 `.last-menu-item` 中找不到父级文案而轮询全量一级菜单并失败。

## 步骤 6：生成用例 JSON

将前几步的产物合并，按以下三份规则文档生成最终的 `ui-cases-{ts}.json`：

| 规则文档 | 作用 |
|----------|------|
| [02_主流程识别与编排.md](02_主流程识别与编排.md) | 确认 mainFlowInventory，决定测哪些 flow |
| [03_菜单导航与步骤.md](03_菜单导航与步骤.md) | 按步骤模板生成 steps，含编排与依赖 |

**关键约束**：
- 每条用例必须有 `trace.flowRefs`，映射到 `mainFlowInventory` 的 `FLOW-*`
- 核心变更的每条操作至少 3 条子用例（正向 + 必填校验 + 取消）
- 关联和回归用例使用步骤 3.2 的通用断言
- 所有 `target` 值（菜单、按钮、字段、弹窗标题、Tab 名）必须来自组件源码原文，逐字一致（含空格和标点），不可凭经验命名
- 输出后不要自动校验（见步骤 7）

---

## 步骤 7：校验确认与执行

用例 JSON 写入完成后，**不要自动执行校验或测试**。先用如下话术询问用户：

```text
UI 用例已生成：<文件路径>

选择下一步操作：
- 执行校验：运行 `node ai-tests/scripts/validate-artifacts.mjs --type ui`，检查用例格式
- 执行测试：需要你提供 --base-url，格式如 `node ai-tests/scripts/run-ui-tests.mjs --base-url https://xxx.com`
- 跳过：暂不校验也不执行

请回复「执行校验」「执行测试」或「跳过」。
```

| 用户回复 | Agent 行为 |
|----------|------------|
| 执行校验 / 校验 | 运行 `node ai-tests/scripts/validate-artifacts.mjs --type ui`，输出通过或失败明细。校验完成后可再询问是否执行测试 |
| 执行测试 / 测试 | 询问用户提供 `--base-url`，然后运行 `node ai-tests/scripts/run-ui-tests.mjs --base-url <用户提供的地址>` |
| 跳过 / 暂不需要 | 不做任何操作；提醒「执行前建议先校验，执行命令：`node ai-tests/scripts/run-ui-tests.mjs --base-url <地址>`」 |
| 未明确回复 | 再次简短询问，不擅自执行或跳过 |
