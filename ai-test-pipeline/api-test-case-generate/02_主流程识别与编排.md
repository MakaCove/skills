# 主流程识别与编排（API）

## 目标

将 `project-analysis.mainFlowCandidates` 转化为 API 用例主流程清单，并编排执行顺序与依赖。

---

## 设计原则

- 主流程覆盖优先于用例数量
- 每个用例必须绑定 `trace.flowRefs`
- 链路依赖使用 `trace.dependsOn` / `trace.produces` / `trace.consumes`

---

## 1. 编排输入

| 输入 | 用途 |
|------|------|
| `coverage.mainFlowInventory[]` | 主流程清单与 `trace.flowRefs` 追溯 |
| `project-analysis.auth` | 登录方式、鉴权头、公共路径 |
| `project-analysis.chainHints.candidateChains[]` | 主流程链路候选 |
| 已生成用例数组 | `request`、`extract`、`trace` |

## 2. 用例类型约束（硬规则）

- 允许：`TC-API-AUTH-*`（登录）与 `TC-API-{MODULE}-{序号}`（业务主流程）
- 禁止：每端点 H/V/A/E 模板、校验失败专项、分页筛选专项、401/403 变体专项
- 每条用例必须有 `trace.flowRefs`，且可在 `mainFlowInventory` 找到

## 3. 变量与依赖补全

### 3.1 变量分类

| 类型 | 示例 | 依赖策略 |
|------|------|----------|
| 系统变量 | `username` `password` `timestamp` | 不加 `trace.dependsOn` |
| 会话变量 | `token` | 由登录用例生产 |
| 业务变量 | `orderId` `projectId` | 由上游用例 `extract/trace.produces` 生产 |

### 3.2 生产者识别

- 登录用例：`extract.token` + `trace.produces: ["token"]`
- 创建/提交类用例：存在 `extract` 或显式 `trace.produces`
- 同变量多个生产者时，优先：主流程 happy 请求 > 更早 tier

### 3.3 消费者补全

扫描 `request.path/headers/body` 中 `{{var}}`：

- 若变量有生产者：补 `trace.dependsOn` 与 `trace.consumes`
- 若鉴权请求且非登录：补登录用例依赖与 `trace.consumes: ["token"]`

## 4. executionTier 规则

| tier | 含义 |
|------|------|
| 0 | `login-bootstrap` |
| 2 | `resource-create` |
| 3 | `resource-read` |
| 4 | `resource-update` |
| 5 | `resource-action` |
| 80 | `resource-delete` |
| 90 | `auth-destructive`（登出/改密等） |

## 5. 拓扑排序

1. 以 `trace.dependsOn` 建图（dep -> case）
2. 先按 `executionTier`，再拓扑排序
3. 写入 `executionOrder: 1..N`
4. 用例数组最终顺序必须与 `executionOrder` 一致

## 6. 输出字段

- 用例级（trace 内）：`trace.dependsOn`、`trace.produces`、`trace.consumes`
- 用例级（根级）：`extract`、`executionTier`、`executionOrder`
- 元信息建议：`coverage.orchestration`

## 7. 验收清单

- [ ] 登录用例在最前（`executionOrder=1` 或 tier=0）
- [ ] 含 `{{orderId}}` 等业务变量的用例均有上游依赖
- [ ] 所有 `trace.dependsOn` 引用存在
- [ ] 无非主流程模板用例（H/V/A/E、分页、校验失败专项）

## 8. 反模式

- 按模块字母序直接排序
- 只写 `trace.consumes` 不写 `trace.dependsOn`
- 业务用例硬编码 `id=1` 或 token
